# DECISIONS.md: merged app

Judgment calls made during the merge, newest at the bottom. Prototype decisions are concatenated at the end in Phase 4.

## Manager decisions before Phase 1

1. **Merged app lives at the repo root**, as prompts/06-merge.md asks. The five prototype folders are inputs and stay untouched. shared/ stays the source of truth and the merge follows CONTRACT_ADDENDUM.md sections A to M.
2. **Billing's store shape is the Db.** One zustand store holds db plus per-surface slices. Billing's engine is the only engine (addendum C1). Every other engine.ts is deleted during the port; surface-only helpers move next to the surface and call the canonical engine.
3. **Theme bridge instead of one Tailwind config per surface.** Tailwind 4 `@theme inline` maps every utility name the five prototypes used to a runtime variable, and each surface's wrapper class sets those variables from its own tokens. This lets five differently styled screens share one build without renaming classes, and lets the storefront keep trashlab.com's language (addendum M) scoped to its subtree while the other four keep the Paper tokens (F1).
4. **Routes by persona.** /owner/pricing, /owner/pricing/quote, /office/account/:accountId, /office/billing, /customer/store/*, /customer/portal. The persona bar is the only cross-surface navigation.
5. **Port 5200 with strictPort**, so the merged app never collides with the five prototypes (5173, 5175, 5179, 5180, 5199) or the check-in hub (5170).

## Phase 1: foundation, shell, and the billing surface

Each entry names the call, the alternative, and the reason.

### Store

6. **Slice contract: flat slices merged into one state** (src/store/slices/types.ts). Each surface's slice is spread flat into the root state next to the core (db, mutateDb, reset). A slice exports a hand-written `interface <Name>Slice` and a `SliceCreator<<Name>Slice>`. `composeSlices` throws at startup, naming both owners, when two slices return the same key or a slice returns a core key. *Alternative:* namespaced slices (`state.billing.cycleDate`), or one zustand store per surface. *Why:* billing's selectors and its 14 test files read flat fields (`s.cycleDate`, `s.db`), so namespacing would have rewritten all of them. Separate stores would split the one Db that the Phase 3 flows depend on. Writing the interfaces by hand avoids a type cycle: a creator's return type refers to RootState, which contains the slice. Key collisions surface as a startup error rather than a silently overwritten action.
7. **One db write path: `mutateDb(fn, patch?)`.** `fn` takes the current db and returns the next one, built from new arrays. `patch`, when given, returns the other store fields to set in the same update. *Alternative:* let each slice call `set({ db })` directly, or add immer. *Why:* one path makes every surface write the same way, and cross-surface writes stay traceable. The engine's writers are already pure (appendCharges, applyPosting, applyWaive), so `fn` composes them as they are. `patch` makes a db write and the UI state it implies (selection, run record, edits) land in one `set`: one render, never a half-applied state. Anything `patch` returns for db is ignored, so `fn` alone decides db.
8. **`reset()` rebuilds every slice from its creator.** It reloads the seed, returns the clock to TODAY, and calls every creator again. That is why creators must be free of side effects. *Alternative:* snapshot the initial state at creation and restore it. *Why:* a snapshot goes stale as soon as a slice adds a field, while re-running the creator cannot forget one. It also means Reset seed in the persona bar clears every surface with no per-surface code.
9. **The engine binds to the live store in useStore.ts, not in the billing slice.** `setEngineDb(() => get().db)` runs once when the store is created. *Alternative:* keep it in billing's slice, where the prototype had it. *Why:* every surface calls the engine, and binding inside one slice would give that slice a side effect and break rule 8.
10. **Billing's store names are kept as aliases.** useStore.ts exports `StoreState` (= RootState) and `initialData()`, and re-exports `DEFAULT_CYCLE_DATE`, `DEFAULT_ACTOR`, and `computePriorChanges`. *Alternative:* rename to the new names and fix every import. *Why:* billing's selectors and tests move unchanged, so they still prove the moved code is the same code.

### Engine

11. **The engine takes an optional trailing `db`** (addendum C2). Every exported engine function that reads the db accepts `db?: Db` as its last parameter. When one is given, the call runs inside `withEngineDb(db, ...)`, and the previous binding is restored afterwards. There are two kinds of exception:
    - *Pure helpers* that never read the db take no db: isBillableException, maxIdSuffix, formatId, dayOf, feeTotal, frequencyLabel, recurringDescription, exceptionLabel, overageTons, setChargeIdGenerator, resetChargeIds.
    - *Db-first functions* keep db as their first, required parameter: nextInvoiceNumber, applyPosting, appendCharges. They are transforms of that db, not reads of the bound one.

    *Alternative:* thread db explicitly through every function and rewrite every caller, or keep the global binding only. *Why:* existing callers and billing's moved tests stay unchanged. Meanwhile, the ports whose prototypes passed state explicitly (account's and pricing's engines) can call the canonical engine against a draft or cloned db without touching the live store.

Changing the generator keeps the two in step. No seeded ServiceEvent has the kind extraPickup, so no billing figure moves (the runbook walkthrough reproduces every figure).

### Style bridge (DESIGN.md)

14. **Every `--rt-*` has a `:root` default.** Tailwind-shipped names default to Tailwind's value. Custom names default to the Paper token (F1). Fonts default to the Paper faces. *Alternative:* no defaults, or Paper values for everything. *Why:* with no default, a bridged utility outside a filled wrapper (placeholders, the shell, a Phase 2 surface half done) resolves to an invalid value and renders unstyled. Tailwind's value is what a prototype got for a name it never defined, so it is the faithful default for those names.
15. **Billing sets every bridged name, though billing uses no Tailwind utilities.** *Alternative:* leave billing on the `:root` defaults. *Why:* a utility added inside billing later renders in billing's own Paper look instead of a Tailwind default. It also gives Phase 2 a complete worked example, and theme.test.ts enforces it.

The earlier bridge missed it: `rounded` compiled to a fixed 0.25rem and ignored storefront's 8px. The `:root` default is 0.25rem (Tailwind's). Billing sets it to `--tl-radius-sm`, mirroring storefront's DEFAULT = sm. *Alternative:* have the storefront port rewrite `rounded` to `rounded-sm`. *Why:* box 1.7 says every borderRadius key is bridged, and the bridge exists so no className is renamed.
17. **Each surface's CSS nests entirely under its wrapper, ground included.** Billing's pattern classes and its former `html`/`body` rules (font, size, color, background) now live on `.surface-billing`. *Alternative:* keep pattern classes global, as each prototype had them. *Why:* portal and billing both define .tl-card, .tl-pill, .tl-table, .tl-drawer, and .tl-money with different rules. Global rules would make whichever loaded last win on both surfaces.
18. **Tailwind scans src/ only** (`@import "tailwindcss" source(".")` in src/index.css). *Alternative:* Tailwind 4's automatic detection from the project root. *Why:* the root contains the five prototype folders. Auto-detection would pull their classes, and their dist and node_modules, into this build.

## Phase 3E: engine, seed, and billing follow-ups (boxes 3.2, 3.2a, 3.2b, 3.7a, 3.7b, 3.7c, 3.7e, 3.7f)

33. **The intake rule, as built** (box 3.2, addendum C13 and L; both Phase 3 agents build against it). *Intake* is every Charge with status proposed or approved that is on no Invoice and whose id is in no billing run's chargeIds (`intakeCharges` in src/store/engine.ts). A charge on a suspended account is not intake until the account is active again (invariant 4); it then joins the next run. `runCycle` (src/store/slices/billing.ts) adds intake to its run after generating: a proposed intake charge joins the queue as a decision of kind `proposedCharge` (never bulk approved, blocks posting until decided, can be approved, edited, or waived like any queue item); an approved one is posted with the run's other approved charges and is not a queue item. `RunRecord` gains `intakeChargeIds`, `intakeDecisionIds`, and `postedAllocations`. Re-running a cycle never deletes or regenerates intake rows, and a charge already in any run is never taken again. On posting, `intakeAllocations` applies prepayments through the canonical `allocate()` in the same update: for each new invoice that carries intake charges, the account's settled Payments that are on no allocation, newest first, up to the smaller of the invoice's open balance and the total of the intake charges on that invoice. This covers storefront's approved first-cycle charges and pay_sf_*, portal's approved extra pickups and pay_p*, and account's proposed reinstatement fees once account writes them to db.charges as proposed Charges. *Alternative:* the literal hand-off wording, "allocate the account's unallocated settled payments up to the invoice's open balance". *Why:* taken literally it auto-applies pay_chk_unknown (the seed's unmatched $65.00 check on acct_res_017, which billing's runbook applies by hand to the older INV-2026-0204) to 017's new October invoice, which moves the Payments tab figures and applies cash to the wrong invoice. Capping at the intake total makes a prepayment pay for exactly the charges it prepaid; newest first means a portal payment is used before an older unrelated one. With no intake in the seed, posting from a clean seed applies nothing and every Payments figure holds (runbook.test.ts pins `postedAllocations: []`).
34. **C13 coverage is period overlap** (boxes 3.2 and 3.2b). `generateRecurringCharges` skips a ServiceItem when a posted or approved recurring Charge for it has a period that overlaps the cycle's period (`coveringCharge`, exported), not only when the start dates match (billing entry 6 is now the special case).
