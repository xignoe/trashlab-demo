## Phase 2: Port the four remaining surfaces (four agents in parallel, each writes only its own folders)

Each agent works only in src/surfaces/<name>/, src/store/slices/<name>.ts, src/styles/surfaces/<name>.css, and its own tests. It may add a route file src/surfaces/<name>/routes.tsx if the surface has sub-routes. It never edits src/store/engine.ts, db.ts, useStore.ts, seed, types, or another surface. If it needs a store-level change it writes the request in DECISIONS.md under "Requests from <name> port" and stubs around it.

Hazards found during Phase 1 that every port must handle:
- Store contract: read src/store/slices/types.ts. Export `interface <Name>Slice` by hand and `const create<Name>Slice: SliceCreator<<Name>Slice>`. Write db only through get().mutateDb(fn). Keys must be unique across the store; billing already owns `edits`, so account's edits sidecar is renamed (for example accountEdits).
- Style bridge: read the header of src/styles/theme.css. Set --rt-* values only inside `.surface-<name>` in src/styles/surfaces/<name>.css. Do not add names to theme.css; request them in DECISIONS.md.
- Duplicate class names: portal defines .tl-card, .tl-pill, .tl-table, .tl-drawer, .tl-money with rules different from billing's. Every surface's component CSS is nested under its `.surface-<name>` wrapper, never global.
- shared/tokens.css has its own @theme block that changes leading-tight and tracking-tight app-wide. If your surface relied on Tailwind's defaults for those, set them back inside your wrapper.
- Photos: account's seed uses /photos/ev_*.svg and portal's uses relative photos/*.svg. Both sets are in public/photos. Use absolute /photos/ paths.
